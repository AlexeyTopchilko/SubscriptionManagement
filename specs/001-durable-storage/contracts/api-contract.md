# Phase 1 Contract: the surface that must not move

**Feature**: [spec.md](./spec.md) · **Plan**: [plan.md](./plan.md) · **Date**: 2026-08-26

This feature adds no endpoint, no field and no status code. The contract below is therefore not
a description of something new — it is the list of things that must be **identical** after the
change, and the reason each one is at risk.

The executable form of this contract is [`docs/api-baseline.md`](../../../docs/api-baseline.md):
29 recorded cases, regenerated by `tools/capture-api-baseline.ps1`. That file is authoritative.
This document explains what it is guarding and why.

---

## Endpoints — all unchanged

| Method | Path | Codes pinned |
|---|---|---|
| `GET` | `/api/customers` | 200 |
| `GET` | `/api/customers/{id}` | 200, 404 |
| `POST` | `/api/customers` | 201, 400, **409** |
| `PUT` | `/api/customers/{id}` | 200, 400, 404, 409 |
| `DELETE` | `/api/customers/{id}` | 204, 404 |
| `GET` | `/api/customers/{customerId}/subscriptions` | 200 |
| `GET` | `/api/customers/{customerId}/subscriptions/{id}` | 200, 404 |
| `POST` | `/api/customers/{customerId}/subscriptions` | 201, 400, 404 |
| `PUT` | `/api/customers/{customerId}/subscriptions/{id}` | 200, 400, 404 |
| `PATCH` | `/api/customers/{customerId}/subscriptions/{id}/status` | 200, 400, 404 |
| `DELETE` | `/api/customers/{customerId}/subscriptions/{id}` | 204, 404 |

No subscription route may lose its `customerId` segment, and no top-level `/api/subscriptions`
route may appear — Principle I.

## Response shapes — unchanged

```
Customer      { id, name, email, company, phone, createdAt, updatedAt, subscriptions[] }
Subscription  { id, customerId, plan, status, price, billingCycle,
                startDate, endDate, createdAt, updatedAt, notes }
```

camelCase property names. Enums as strings. Optional fields present with `null`, never omitted.

## The seven things most likely to break, and what each looks like

Each of these passes a build, starts the application, and returns 200.

| # | Invariant | The break to watch for | Guard |
|---|---|---|---|
| 1 | `price` keeps its submitted form | `4900` → `4900.0` or `4900.00` | Baseline. **Already measured to happen on SQLite** — this is why the provider is PostgreSQL with unconstrained `numeric` |
| 2 | `status` is a string | `"Active"` → `0` | Baseline cases 13–25 |
| 3 | Optional fields are `null`, not absent | `"notes": null` → key missing | Baseline |
| 4 | `billingCycle` is lower-cased on write | `MONTHLY` stored as sent | Baseline case 13 sends upper case on purpose |
| 5 | Duplicate email is **409**, not 500 | A unique index turning a conflict into `DbUpdateException` | Baseline case 9. Mitigated by design: no unique index is added — see [data-model.md](./data-model.md) |
| 6 | Validation rejections stay **400** | Storage-level constraints turning them into 500 | Baseline cases 7, 8, 14–17. Mitigated by keeping validation in services only |
| 7 | `PUT` does not touch `status` | Full-update overwriting status with a default | Baseline case 18 |

## Timestamps — the one gap in the automated guard

The baseline normalises timestamps to `<timestamp>` so reruns are byte-identical. That means it
**cannot** detect:

- a timezone shift (a UTC value coming back as local, or vice versa)
- a precision loss (sub-second digits truncated)

Moving from an in-memory `DateTime` to a `timestamp with time zone` column is exactly the kind of
change that causes both. This must be checked **by hand** — see [quickstart.md](./quickstart.md).

## Collection ordering — the single declared change

`ORDER BY createdAt, id` for customers, and for subscriptions within a customer.

One permitted change, declared in advance in the spec: one demonstration customer holds two
subscriptions whose insertion order does not match their creation times, so they swap position.

It surfaces in **four** baseline cases, not three. Cases 1 and 2 embed the customer's subscription
list; case 4 lists it directly; and case 5 asks for the *first* subscription of that customer, so
after the swap it returns a different subscription altogether — different plan, price, status and
notes. The capture script selects `subscriptions[0]`, which is why the reordering propagates into
what looks like a single-record lookup.

**Any other difference is a regression.** The declared swap is the only entry on the allow-list,
and the allow-list is closed — a difference explained after the fact is a regression that was not
worth fixing, not a decision.

## Explicitly not fixed here

404 responses currently come in two shapes — RFC 9110 problem details from the bare `NotFound()`
on read paths, and `{ "message": ... }` from the paths that switch on a result type. Tracked as
ALE-15.

The baseline pins **both** shapes as they are. Correcting the inconsistency inside this feature
would put an intended contract change into the very diff whose emptiness is the proof that
nothing else moved.

## Out of scope

No change to `frontend/src/api/index.js` or anywhere else in the SPA. If the frontend needs
editing, the contract moved and something in this plan is wrong.
