# Phase 1 Data Model: Durable storage for customers and subscriptions

**Feature**: [spec.md](./spec.md) · **Plan**: [plan.md](./plan.md) · **Date**: 2026-08-26

Two tables. The entities themselves are **not changing** — `Models/Customer.cs` and
`Models/Subscription.cs` stay exactly as they are, including property order, nullability and
types. This document records how they map to storage and which mapping choices are load-bearing.

---

## The three mapping choices that carry risk

### 1. `Price` is `numeric` with no precision or scale

This is the decision the provider choice was made for. Measured in
[research.md](./research.md): a fixed scale pads every amount to that many decimal places, so
`numeric(18,2)` returns `4900` as `4900.00`, and `System.Text.Json` puts that on the wire. The
baseline pins `"price": 4900`.

Unconstrained `numeric` stores the submitted form exactly — verified against a live database,
including `4900` staying `4900`, `12345678.90` keeping its trailing zero, and `0.005` surviving
at three decimal places.

**Do not add a precision or scale to this column.** It looks like tightening and it is a contract
break.

### 2. `Status` is stored as an integer, so the enum's declaration order is now a storage contract

```csharp
public enum SubscriptionStatus { Active, Paused, Cancelled, Future }
//                               0       1       2          3
```

Rows hold `0`–`3`. Reordering these members, or inserting a new one anywhere but the end, silently
reinterprets every stored row — a `Cancelled` subscription would read back as something else.
Nothing would fail; the data would just be wrong.

This is a new hazard created by this feature. Before it, the enum order was a purely in-process
detail. It is worth a comment on the enum itself, and it is the reason the JSON layer keeps
serialising by *name*: the wire contract is insulated from the storage encoding.

An alternative is storing the name as text, which removes the hazard at the cost of a wider
column and a conversion. Not chosen, because the integer mapping is EF Core's default and
changing it is a bigger diff than a comment plus this note.

### 3. Email uniqueness is enforced in the service, not by a unique index

The service already checks for a duplicate email and returns a conflict, which the controller
maps to **409** — baseline case 9 pins it.

Adding a unique index would move that failure: the insert would throw a
`DbUpdateException`, reach `GlobalExceptionMiddleware`, and surface as **500**. That is a contract
break, and a bad one — a client's legitimate mistake reported as a server fault.

So the index is deliberately **not** added. The cost is that a true race between two identical
emails could insert both, consistent with the last-write-wins position taken in FR-022. Recorded
as a known limit rather than fixed, because fixing it means changing the response contract.

## Validation stays in services

Columns are as permissive as the model allows. `Name` and `Email` are non-nullable because the
CLR properties are, but nothing at the storage level rejects an empty string, a negative price, or
an end date before its start.

That is Principle III: repositories persist and retrieve, services enforce rules. Duplicating the
rules into check constraints would create two places that can disagree — and the storage-level
copy would report violations as 500s rather than the 400s the baseline pins.

## State transitions

Unchanged and untouched by this feature. `SubscriptionService.ValidateStatusTransition` remains
the only place the transition table exists:

- `Future` → `Active` | `Cancelled`
- `Active` → `Paused` | `Cancelled`
- `Paused` → `Active` | `Cancelled`
- `Cancelled` → terminal
- any status → the same status: permitted no-op, including `Cancelled` → `Cancelled`

Storage has no opinion on transitions and must not acquire one — a trigger or check constraint
here would move rejections from 400 to 500.

## The aggregate boundary in practice

Principle I binds the access path, not the schema. Concretely:

- `AppDbContext` exposes `DbSet<Customer>` only. There is no `DbSet<Subscription>`.
- Every `ISubscriptionRepository` method keeps `customerId` in its signature — unchanged from
  today.
- Reads load the customer with `Include(c => c.Subscriptions)` and select from that graph.
- Writes mutate the tracked customer and call `SaveChanges` once, so the aggregate is one unit
  of change (FR-002).
- Deleting a customer removes its subscriptions by cascade, satisfying FR-003 in the schema
  rather than relying on application code remembering (FR-003).

## Seeding

Three customers and five subscriptions, written **only when the customer count is zero**
(FR-004). Not EF Core's `HasData`: model seeding reconciles on every migration, which would
resurrect a demonstration customer someone deleted — violating FR-004 and User Story 1
scenario 3.

The seeded values, including their `CreatedAt` timestamps, must be preserved exactly as the
current `InMemoryCustomerRepository.SeedData()` writes them. The baseline depends on them, and
one of them is the reason the declared ordering swap exists: one customer's two subscriptions
have creation times in the opposite order to their insertion.
